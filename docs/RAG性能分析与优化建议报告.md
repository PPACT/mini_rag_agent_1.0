## 二、当前性能数据

### 耗时分解

| 模块 | 耗时 | 占比 |
|---|---|---|
| 歧义判定（LLM） | 2336 ms | 56.7% |
| 答案生成 | 1286 ms | 31.2% |
| 检索（混合检索+RRF融合） | 498 ms | 12.1% |
| **后端合计** | **4120 ms** | 100% |
| 客户端真实往返 | 4137 ms | — |

### 当前链路

```
用户Query
  → LLM歧义判定（2336ms）
  → 并行：BM25词法检索 + ANN(HNSW)向量检索
  → RRF融合两路结果（合计498ms）
  → ❌ 跳过CrossEncoder精排
  → LLM生成答案（1286ms）
```

## 三、瓶颈定位

### 🔴 最大瓶颈：歧义判定 LLM（2336ms）

- 占总耗时 **56.7%**，是最大延迟来源
- 属于检索前置的独立 LLM 调用，用于 query 意图识别 / 模糊性判断
- 使用了大模型做轻量判定，性价比极低

### 🟡 次要模块：答案生成（1286ms）

- 占总耗时 31.2%
- **`DeepSeek 云 API` 生成**（❌ 非本地 LLM —— 原报告此处有误；延迟含网络往返）
- 取决于模型大小、网络状况与返回长度

### 🟢 检索模块：498ms（良好水平）

- 混合检索（BM25 + HNSW ANN + RRF 融合）合计 498ms
- 属于**良好**区间（参考：优秀 <200ms，良好 200~600ms，一般 600~1200ms）
- 单路 HNSW 向量检索一般在 100~300ms，当前包含两路召回 + RRF 融合，表现不错

### ⚪ 精排：未启用

- 使用 BAAI/bge-reranker-base（Cross-Encoder）
- 开启后预计额外增加 **100~400ms** 耗时
- 提升召回质量，但不影响检索本身耗时

## 四、优化建议（按优先级排序）

### 🔴 P0：歧义判定模块优化（收益最大）

| 方案 | 说明 | 预期收益 |
|---|---|---|
| **改为门控（推荐）** | 保留歧义判定能力，**仅在"可能歧义"时调 LLM** | 多数请求砍掉 ~1.8s |
| ~~直接移除~~ | ⚠️ **不推荐**：会丢失"候选矛盾时主动澄清"能力（曾用于解决"指标全绿但业务全错"） | 砍掉 ~2.3s 但能力归零 |
| 替换为轻量小模型 | 用小模型 / 分类器做歧义判断 | 砍到 200~500ms（准确率待验证） |
| 规则 / 关键词判断 | 简单场景用规则替代 LLM | 砍到 50~100ms（能力大幅下降） |
| ~~异步并行执行~~ | ❌ **不可行**：歧义判定**依赖检索结果**（需判断"候选之间是否矛盾"），存在数据依赖，无法并行 | — |

**风险评估**：需确认业务是否必须做歧义判定，去掉后需观察问答效果是否下降。

### 🟡 P1：精排性能优化（后续开启精排时使用）

| 方案 | 说明 |
|---|---|
| ONNX 量化 | bge-reranker-base 做量化推理，提速 30~50% |
| 减少候选数量 | 只取 top10~top16 送入精排，而非 top32 |
| 批量推理优化 | 确保使用 GPU batch 推理，而非逐条推理 |

### 🟢 P2：检索侧微调（收益有限）

| 方案 | 说明 |
|---|---|
| ~~降低 HNSW ef_search~~ | ⚠️ **勿降**：实测 pgvector 默认值 40 已导致 **ANN@1 仅 0.860**（14% 的查询 top-1 出错），本项目已显式提到 **100**；再降会更糟 |
| 控制召回数量 | 减少 BM25 / 向量两路的候选召回数，降低 RRF 计算量 |
| 向量降维 | 如果 embedding 维度较高（如 1536/3072），可考虑 PCA 降维 |

## 五、优化后参考链路

```
用户Query
  → （可选）轻量意图识别 / 规则判断（<500ms）
  → 并行：BM25词法检索 + ANN(HNSW)向量检索
  → RRF融合两路结果
  → （可选）CrossEncoder精排（bge-reranker-base）
  → LLM生成答案
```

## 六点五、补充：本项目已有实测数据（原报告未掌握）

以下均为本项目已完成实验的**实测结论**，供修订建议时参考——避免重复已证伪的方案：

| 项 | 实测结论 |
|---|---|
| **歧义判定现状** | 漏报 **59.5%** / 误报 2.5%（判定器收紧后，80 清晰题 + 37 歧义/对抗题）；⚠️ 且修复前**约半数调用的结论被静默丢弃**（推理模型思考吃满 `max_tokens` → `content` 为空 → 回退"不歧义"），详见 2026-09-19 记录 |
| **门控已有失败尝试** | "候选来源分散度 ≥3" 试过 → **通过率 98%**，形同虚设（规模下 top-5 几乎总跨多文档） |
| **MMR** | 已诊断：近似块"挤占"仅影响 **3.8%** 的题 → 收益有限，**已跳过** |
| **精排三方对比** | 粗排 85.0% ｜ LLM 精排 88.8%（**11s**）｜ 本地 cross-encoder **87.5%**（0.78s） |
| **本地精排已知缺陷** | 3 个误杀（LLM 为 0），其中 1 个严重（正确答案掉出候选） |
| **启动开销** | 已优化 37s → 16s（消除 HF 联网检查 + Ollama 冷启动） |
| **ef_search** | 默认 40 丢 14% top-1 → 已提到 100（+3.7ms 换回满召回） |

> 结论：**歧义判定的门控是当前最高价值的方向**，但**必须靠数据选信号**——
> 上次"来源分散度"就是拍脑袋定的阈值，结果失败。

## 七、附：关键概念速查

| 名词 | 阶段 | 作用 |
|---|---|---|
| ANN（HNSW） | 向量检索 | 从海量向量库快速召回语义相似 chunk |
| BM25 | 词法检索 | 基于关键词匹配召回 chunk |
| RRF | 结果融合 | 合并 BM25 + ANN 两路召回结果 |
| CrossEncoder（bge-reranker-base） | 精排 | 精细判断 query-chunk 相关性，重排序 |
| MMR | 后处理 | 剔除语义重复 chunk，提升多样性 |
| 歧义判定 LLM | 前置处理 | 判断 query 是否模糊 / 需要追问 |
