# docs/ 说明

## 文档放置规则

> **与 RAG 业务无关的开发文档，一律放 `docs/`，不要散落在项目根目录。**

**例外**（功能性要求，必须留根目录）：

| 文件 | 为什么必须在根目录 |
|---|---|
| `CLAUDE.md` | Claude Code 只从项目根加载此约定，移走即失效 |
| `README.md` | 仓库门面，约定俗成 |

> 这条规则是为了修一个真实发生过的问题：开发文档曾散落在根目录（计划、规划、回顾各一处）。
> 根因是**隐式约定会被侵蚀**——所以写下来，而不是靠记忆。

## 这个目录是什么

**项目开发文档**——给人看的：方案、记录、评估、计划。与系统的运行时行为**完全无关**。

## 这个目录不是什么

⚠️ **不是 RAG 知识库的原始文本。** `docs/` 里的任何内容都不会被 RAG 系统读取、解析或向量化。

对 RAG 项目来说 `docs` 这个名字确实容易误读，特此明确边界：

| 内容 | 位置 | 性质 |
|---|---|---|
| **项目开发文档** | `docs/`（本目录） | 给人看的，与运行无关 |
| **RAG 知识库文本**（用户上传的） | `data/uploads/` | 业务数据，gitignore |
| **RAG 测试语料**（评测夹具） | `eval/corpus/`、`eval/corpus_synth/` | 测试用，与线上知识库无关 |
| **接口文档** | 运行时 `/docs`（FastAPI 自动生成） | OpenAPI，非本目录 |

## 文件清单

| 文件 | 内容 | 是否上传 |
|---|---|---|
| `README.md` | 本说明 | ✅ 公开 |
| `架构方案.md` | 系统设计：定位/选型/分层/数据模型/链路/扩展点 | ✅ 公开 |
| `开发记录.md` | 开发过程、踩坑记录、编码约定 | ✅ 公开 |
| `改进计划.md` | 改进事项追踪（按优先级，完成后勾选） | 🔒 本地留存 |
| `RAG生产化回顾.md` | 复盘手册：能力分层、量级参考、上线硬指标、行业边界 | 🔒 本地留存 |
| `资源规划.md` | 本地资源账本：显存预算、红线、未来功能开销 | 🔒 本地留存 |
| `评估报告.md` | 对架构方案的独立评估（含未完成项） | 🔒 本地留存 |

> 「本地留存」的文件已在 `.gitignore` 中排除，不进公共仓库。
> 需要公开时，先检查内容是否含本地路径、机器信息等。
