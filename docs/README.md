# docs/ 说明

## 文档放置规则

> **与 RAG 业务无关的开发文档，一律放 `docs/`，不要散落在项目根目录。**

**例外**（功能性要求，必须留根目录）：

| 文件 | 为什么必须在根目录 |
|---|---|
| `CLAUDE.md` | Claude Code 只从项目根加载此约定，移走即失效 |
| `README.md` | 仓库门面，约定俗成 |

> 这条规则是为了修一个真实发生过的问题：开发文档曾散落在根目录（计划、规划、回顾各一处）。
> 根因是**隐式约定会被侵蚀**——所以写下来，而不是靠记忆。

---

## 这个目录是什么

**项目开发文档**——给人看的：方案、记录、计划、评估。与系统的运行时行为**完全无关**。

## 这个目录不是什么

⚠️ **不是 RAG 知识库的原始文本。** `docs/` 里的任何内容都不会被 RAG 系统读取、解析或向量化。

对 RAG 项目来说 `docs` 这个名字确实容易误读，特此明确边界：

| 内容 | 位置 | 性质 |
|---|---|---|
| **项目开发文档** | `docs/`（本目录） | 给人看的，与运行无关 |
| **RAG 知识库文本**（用户上传的） | `data/uploads/` | 业务数据，gitignore |
| **RAG 测试语料**（评测夹具） | `eval/corpus/`、`eval/corpus_synth/` | 测试用，与线上知识库无关 |
| **接口文档** | 运行时 `/docs`（FastAPI 自动生成） | OpenAPI，非本目录 |

---

## 文档地图

> **维护约定**：每份文档都声明**自己的权威范围**。
>
> **对外可见的三份**（即本仓库里实际能读到的）之间的裁决规则：
> **看「系统长什么样」→ `架构方案.md`；看「当时为什么这么选、踩过什么坑」→ `开发记录.md`。**
> 标 🔒 的文档**不在本仓库**；**内部维护者**的裁决规则见 `docs/交流协议.md`
> （原在本文件，2026-09-26 迁出——见下方「关于本目录的完整性」）。
>
> 历史教训：本目录曾同时存在 4 份互不标注时效的「现状描述」，读者无法判断该信哪份。
> **因此每份文档都必须写清"我负责回答什么、我不负责什么"。**

| 文件 | 权威范围（只答这一个问题） | 上传 |
|---|---|---|
| `README.md` | **本说明**：文档放在哪、边界在哪、谁是权威 | ✅ 公开 |
| `架构方案.md` | **系统现在长什么样**：定位 / 选型 / 分层 / 数据模型 / **真实链路** / 扩展点 / 已知边界 | ✅ 公开 |
| `开发记录.md` | **当时为什么这么选、踩过什么坑**：搭建过程、6 个 bug、编码结论、关键设计决策、立项期评估存档 | ✅ 公开 |
| `优化方案.md` | **现在是什么样 / 瓶颈在哪 / 下一步做什么**：现状基线（唯一权威）、性能/效果/度量三类瓶颈、分优先级方案、取舍矩阵、待复核清单、行业参照系 | 🔒 本地留存 |
| `改进计划.md` | **每件事做到哪一步了**：逐项追踪与勾选，**实时性最高** | 🔒 本地留存 |
| `交流协议.md` | **我们怎么协作**：**规则层**——权责划分、git 规则（提交交开发侧）、查看节奏、交流区释放机制、异议编号与答复格式、交付与防错约定 | 🔒 本地留存 |
| `交流区.md` | **当前在议什么**：**工作层**，**易失**——合作点完成后压缩归档为一行 | 🔒 本地留存 |
| `资源规划.md` | **加新组件前查表**：显存 / 内存 / 磁盘预算、三条红线、CPU 降级策略 | 🔒 本地留存 |
| `交流区归档.md` | **某条结论为何成立**：已释放议题的证据（append-only）。⚠️ **不主动读**（协议 §6.5 RD-5），按议题号 `grep` 一行 | 🔒 本地留存 |
| `RAG 管线调参与评估检查清单.md` | **通用调参与评估方法论**（跨项目参考）：总览 / 清洗 / 切分 / 元数据 / 存储 / 向量检索 / 召回 / 精排 / 改写 / 分层评估 + **经验数字的局限**。⚠️ **不含本项目事实**——与 `优化方案.md` 的实测冲突时，**以 `优化方案.md` 为准** | 🔒 本地留存 |

## 关于本目录的完整性

⚠️ **本目录的文件不是全部。**

- 下列文档**内部维护用、未随本仓库发布**：`优化方案.md`、`改进计划.md`、`资源规划.md`、
  `交流协议.md`、`交流区.md`、`交流区归档.md`、`RAG 管线调参与评估检查清单.md`。
- 它们的**权威范围**仍列在上表（标 🔒）——**便于你知道"存在这样一份文档、它负责回答什么"**，
  而不是让你去找一个打不开的文件。需要时请向项目维护者索取。
- **内部维护者**的裁决规则、协作流程与 `.gitignore` 注意事项，见 `docs/交流协议.md`。

> 本仓库实际可读的开发文档只有上面标 ✅ 的三份：
> `README.md`（本说明）、`架构方案.md`（系统设计）、`开发记录.md`（过程与决策记录）。
