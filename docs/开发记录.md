# RAG-Demo 开发记录与踩坑笔记

> 记录本项目从零搭建到端到端跑通的完整过程、关键设计决策、验证过程中踩过的坑，以及编码问题的结论。用于后续回顾与交接。

## 1. 项目概览

B端企业内部知识库 RAG-Agent Demo。本地免费部署为主，LLM 走 DeepSeek 云 API（测试成本可控）。

**技术栈**：
- Web：FastAPI + Uvicorn
- 向量库：PostgreSQL 17 + pgvector（单库，不做跨库双库）
- 缓存/任务：Redis + Arq
- Embedding：本地 Ollama `bge-m3`（1024 维，CUDA，模型迁到 独立目录）
- LLM：DeepSeek `deepseek-v4-flash`（LiteLLM 配置收口，实际经 ChatOpenAI 调用）
- Agent：LangGraph + MCP（Mock FastMCP 服务模拟员工信息查询）

**6 大需求全部验证通过**：①文档异步上传解析切块向量化 ②RAG 问答+权限过滤 ③Redis 会话缓存 ④MCP 工具演示链路 ⑤权限字段预留 ⑥平滑迁移预留。

## 2. 环境与启动

### 2.1 环境约定（重要）
- conda 隔离环境 `mini_pg_agent`，Python 3.11.16。
- **禁止裸用 python / pip**，一律完整路径：
  - Python：`~/miniforge3/envs/mini_pg_agent/python.exe`
  - uv：`~/.local/bin/uv.exe`
  - pip（兜底）：`~/miniforge3/envs/mini_pg_agent/Scripts/pip.exe`
- 装包：`uv pip install --python <python完整路径> <包名>`
- Ollama 模型已迁到 独立目录（见 2.3）。

### 2.2 三步启动
```bash
# 1. 基础设施
docker compose up -d
# 2. Ollama（bge-m3 已在 独立目录）
ollama serve
# 3. 建表 + 起服务
psql "postgresql://rag:rag_demo_pwd@localhost:5432/rag_demo" -f src/db/init_db.sql
PYTHONIOENCODING=utf-8 python -m uvicorn src.main:app
PYTHONIOENCODING=utf-8 python -m arq src.tasks.worker.WorkerSettings
```

### 2.3 Ollama 模型迁出默认目录
默认模型在 `~/.ollama/models`，已改为独立目录：
- 环境变量 `OLLAMA_MODELS=~/ollama_models`（用户级，已设）。
- 跑 ollama 命令时若当前 shell 未继承该变量，先 `export OLLAMA_MODELS="~/ollama_models"`。

## 3. 架构与关键设计决策

### 3.1 分层
```
src/
├── config/     # settings(pydantic-settings) / litellm_client / prompts
├── db/         # asyncpg 连接池 + init_db.sql
├── cache/      # Redis 缓存
├── tasks/      # Arq worker + document_task + queue
├── document_parser/  # loader(pdf/docx/pptx) + semantic_splitter(结构化切块)
├── embedding/  # BaseEmbedding → OllamaEmbedding / CloudEmbedding(占位)
├── vector_store/     # VectorStore → PgVectorStore / MilvusStore(桩) + AccessFilter
├── rag/        # retriever(检索 + 权限过滤)
├── agent/      # graph_builder(LangGraph) + mcp_mock_server(FastMCP) + client
├── schemas/    # Pydantic DTO
├── api/        # upload_api / chat_api
└── observability/    # 审计日志 tracer + OTel 占位
```

### 3.2 数据模型（关键字段）
- `documents`：id / filename / **status**(pending→processing→completed/failed/deleted) / version / chunk_count / error / created_at / **updated_at** / **is_deleted**
- `chunks`：id / document_id(FK CASCADE) / chunk_index / document_version / content / embedding(vector(1024)) / **department** / **secret_level** / source_file / create_time / **updated_at**

**一致性规则**：增删改包同一事务；更新=同事务删旧插新+版本号+1；删除=软删 `is_deleted=true`；检索一律 `is_deleted=false`；HNSW 索引 + (department,secret_level) 索引。

### 3.3 关键设计决策
1. **RAG 管道手写，只有 Agent 编排用框架（LangGraph）**。原因：为"模块解耦 + 预留扩展口子 + 可替换"服务，`BaseEmbedding`/`VectorStore`/`AccessFilter` 抽象层要自己掌控；框架会把抽象藏起来，不利于后期切 Milvus / 云 embedding。
2. **LLM 用 `langchain_openai.ChatOpenAI` 指向 DeepSeek**（DeepSeek 是 OpenAI 兼容），而非 LiteLLM 直接调用。原因：LangGraph 工具调用需要 LangChain 聊天模型，ChatOpenAI 最稳；`litellm_config.yaml` + `litellm_client.py` 保留作为路由/切换文档。
3. **抽象层为平滑迁移铺路**：`BaseEmbedding`（切云 embedding）、`VectorStore`（切 Milvus）、`AccessFilter`（两引擎过滤语义统一）、`VECTOR_STORE` 配置开关。
4. **Milvus 迁移用蓝绿策略，不搞永久双写**：平时单写 PG（事实源），迁移时倒灌 + 短暂双写 + 切配置 + 回滚；PG 索引永不删，作回滚快照。`updated_at`/`is_deleted` 就是为增量同步预留的。

## 4. 验证踩坑记录（6 个 bug）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | `GET /documents/{id}` 返回 500 | SQL `id::text` 列名是 `id`，模型要 `document_id` | 改成 `id::text AS document_id` |
| 2 | API 启动失败 `NotImplementedError` | langchain-mcp-adapters 0.1.0+ 的 `MultiServerMCPClient` 不能 `async with` | 去掉 `__aenter__/__aexit__`，直接 `get_tools()` |
| 3 | key 解析成 `# TODO: 用户自填`，LLM 报 `UnicodeEncodeError` | `.env` 里 `DEEPSEEK_API_KEY=  # TODO` 的行内注释被 python-dotenv 当成值 | 注释独立成行，key 置空 |
| 4 | 空 key 下 API 启动失败 `Missing credentials` | langchain-openai 1.6 在**构造** ChatOpenAI 时就校验 key | key 为空时跳过 agent 构建（懒初始化），/chat 返回 503 |
| 5 | 问答检索返回空 | 上传接口没接受 department/secret_level，chunk 元数据为 NULL，权限过滤把它排除了 | 上传接口加 `department`/`secret_level` Form 字段，传到 chunk |
| 6 | 新文档入库后老问题仍返回旧空结果 | 上传后没作废 Redis 缓存，旧结果被命中 | document_task 处理完成后调 `invalidate_cache()` |

**通用教训**：新版本库（langgraph/langchain-openai/langchain-mcp-adapters）API 变化大，写代码前先 introspect 实际签名，别照搬旧文档。

## 5. 编码问题结论

**数据从头到尾就是 UTF-8**，没有乱码问题：
- PG `server_encoding/client_encoding = UTF8`（已确认）
- 代码源文件 UTF-8、`open(..., encoding='utf-8')` 显式声明、Redis `decode_responses=True`、FastAPI JSON 默认 UTF-8

**"乱码"纯粹是终端显示问题**：Windows 控制台默认代码页是 GBK(cp936)，和 UTF-8 对不上。数据本身正确（实测 `'员工' in chunk.content` 为 True）。

**解决**：运行会打印中文/日志的脚本时加 `PYTHONIOENCODING=utf-8`（bash 前缀 / PowerShell `$env:PYTHONIOENCODING="utf-8"`）。

**企业标准分层做法**：数据层 UTF8 + client_encoding、代码层显式 UTF-8、传输层显式 `charset=utf-8`、文档解析约定源文件 UTF-8（纯 txt 是主要坑）、显示层控制台代码页 65001。

## 7. 知识库治理方向（路线图，暂不实现）

知识库"内容治理"是独立于检索/生成的一大块工作，方向已明确但当前 demo 不实现，记录如下：

- **局部更新**：仅"原地替换无偏移"时才有意义，有增删即退回全量重建；收益只省当前文档算力，不能替代跨文档核查。
- **跨文档过期核查**：改文档 → 用变更知识点检索全库 → 输出"其他文档疑似过期 chunk"清单，人工核查。
- **治理工作流**：待改文档优先级排序（时效性/业务权重/匹配置信度/使用热度）、文档内定位辅助 + 编辑草稿、分批 + SLA + 分责任人、用户反馈通道、离线一致性巡检。
- **中心化公共知识库 + 模板化文档**：治本，但依赖文档写作规范（组织问题，非技术）。

**关键原则**：❌ 不自动改写原始文档；❌ 不靠重 embedding 修事实错误。局部更新收益有限，真正的成本在"跨文档事实冲突 + 人工核查"。

## 8. 立项期评估（历史存档）

> **性质**：2026-09-10 的一份"资深 Agent 从业者视角"独立评估，针对当时的 `架构方案.md`。
> **这是历史快照，不是现状**——其中大部分建议后续已完成、已证伪或被更准的实测取代。
> **保留它的价值**：记录"项目起点长什么样"以及"当时的判断哪些对、哪些错"。
> **现状请以 `优化方案.md` §1 为准。**

### 8.1 当时的总评

| 维度 | 评分 | 说明 |
|---|---|---|
| 工程规范 | A- | 分层、抽象、迁移、测试、锁版本、隐私卫生——超出普通 demo |
| 数据与一致性 | A- | 事务、版本、软删、级联，细节到位 |
| 安全边界 | B | 鉴权 + 部门隔离已闭环，但模型过简、无注入防护 |
| **RAG 质量** | **C** | 朴素 RAG：无改写、无重排、无阈值、无评测 |
| **Agent 智能** | **C+** | 检索不是 Agent 的工具，只是前置步骤 |
| 运维可观测 | C | 日志 stdout、观测占位、无降级、无扩展 |

**当时的结论**：「工程骨架优秀、但检索与推理内核需要重做」。

**当时认为做得好的（至今仍然成立，不必动）**：
1. **抽象层是真抽象**——迁移只改实现类，业务零改动；
2. **数据一致性想到了企业级细节**——同事务替换、版本号、软删、`is_deprecated`、级联删除；
3. **权限过滤在服务端**——不信任客户端参数，这个边界守对了；
4. **工程可复现**——锁版本 + Alembic + 单元测试，换机器能重建。

### 8.3 ⚠️ 本文档体系的一个教训

那次评估与后来的实测出了**一批方向性偏差**（A1/A2/A3 三处），共同原因是
**在没有任何端到端评测的情况下做架构判断**。这不是评估者水平问题——
**没有度量的架构评审，本质上是猜测**。这也是后来把 `eval/` 定为最高优先级的根本理由。
