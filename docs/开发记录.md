## 1. 项目概览

B端企业内部知识库 RAG-Agent Demo。本地免费部署为主。

**技术栈**：
- Web：FastAPI + Uvicorn
- 向量库：PostgreSQL 17 + pgvector（**两库物理隔离**：`rag_real` 15432 / `rag_stress` 15433）
- 缓存/任务：Redis + Arq
- Embedding：本地 Ollama `bge-m3`（1024 维，CUDA，模型迁到 独立目录）
- LLM：**任意 OpenAI 兼容服务**（`litellm_config.yaml` 收口，实际经 ChatOpenAI 调用）
  —— **已解除厂商绑定**（自测用 DeepSeek）
- Agent：LangGraph + MCP（Mock FastMCP 服务模拟员工信息查询）
- 文档解析：**三层路由**（pdfplumber / python-docx / openpyxl / python-pptx / 纯文本兜底）

**6 大需求全部验证通过**：①文档异步上传解析切块向量化 ②RAG 问答+权限过滤 ③Redis 会话缓存 ④MCP 工具演示链路 ⑤权限字段预留 ⑥平滑迁移预留。

**2.0 阶段 0 已完成**：三层路由 · 表格入库 · 页码元数据 · 解析失败显式报错（详见 §3.4）。

## 3. 架构与关键设计决策

### 3.1 分层
```
src/
├── config/     # settings(pydantic-settings) / litellm_client / prompts
├── db/         # asyncpg 连接池 + init_db.sql
├── cache/      # Redis 缓存
├── tasks/      # Arq worker + document_task + queue
├── document_parser/  # routing(三层路由) + parsers + tables + blocks(IR)
│                     # + chunking(块级切块) + semantic_splitter + tokenizer
├── embedding/  # BaseEmbedding → OllamaEmbedding / CloudEmbedding(占位)
├── vector_store/     # VectorStore → PgVectorStore / MilvusStore(桩) + AccessFilter
├── rag/        # retriever(检索 + 权限过滤)
├── agent/      # graph_builder(LangGraph) + mcp_mock_server(FastMCP) + client
├── schemas/    # Pydantic DTO
├── api/        # upload_api / chat_api
└── observability/    # 审计日志 tracer + OTel 占位
```

### 3.2 数据模型（关键字段）

> 迁移 **0001 ~ 0005**。⚠️ 建表**一律用 `scripts/migrate_all.py`**（两个库都迁 + 逐表比对 schema）；
> `alembic upgrade head` **只会迁一个库**，`src/db/init_db.sql` 是 1.0 的、**缺后续迁移的列**。

- `documents`：id / filename / **original_name** / status / version / chunk_count / error / created_at / updated_at / is_deleted
- `chunks`：id / document_id(FK CASCADE) / chunk_index / document_version / content / embedding(vector(1024)) / **content_tsv** / department / secret_level / source_file / start_offset / end_offset / title / **page** / **raw_table** / **table_complex** / is_deprecated / create_time / updated_at

**2.0 新增的三列（迁移 0005）**：

| 列 | 来源 | 用途 |
|---|---|---|
| `page` | PDF 逐页解析（1-based） | 引用可答"第几页"。⚠️ **Word/Excel 为 `NULL`**，**不编造页码** |
| `raw_table` | 表格块的**原表 Markdown** | **只进词法** `content_tsv`，**不进向量** |
| `table_complex` | 表格复杂度判定 | 这类表的**原表也进向量**；评测能分开看 |

**一致性规则**：增删改包同一事务；更新=同事务删旧插新+版本号+1；删除=软删 `is_deleted=true`；检索一律 `is_deleted=false AND is_deprecated=false`；HNSW 索引 + `content_tsv` GIN + (department,secret_level) 索引。

### 3.3 关键设计决策
1. **RAG 管道手写，只有 Agent 编排用框架（LangGraph）**。原因：为"模块解耦 + 预留扩展口子 + 可替换"服务，`BaseEmbedding`/`VectorStore`/`AccessFilter` 抽象层要自己掌控；框架会把抽象藏起来，不利于后期切 Milvus / 云 embedding。
2. **LLM 用 `langchain_openai.ChatOpenAI` 指向任意 OpenAI 兼容服务**（`litellm_config.yaml` 收口），而非 LiteLLM 直接调用。原因：LangGraph 工具调用需要 LangChain 聊天模型，ChatOpenAI 最稳。**已解除厂商绑定**（D8）—— 换服务只改配置。
3. **抽象层为平滑迁移铺路**：`BaseEmbedding`（切云 embedding）、`VectorStore`（切 Milvus）、`AccessFilter`（两引擎过滤语义统一）、`VECTOR_STORE` 配置开关。
4. **Milvus 迁移用蓝绿策略，不搞永久双写**：平时单写 PG（事实源），迁移时倒灌 + 短暂双写 + 切配置 + 回滚；PG 索引永不删，作回滚快照。`updated_at`/`is_deleted` 就是为增量同步预留的。
5. **表格 = 一份检索面 + 一份随行**：`content` 是自然语言版（进向量 + 词法），`raw_table` 是原表 Markdown（**只进词法**）。
   原因：① **裸表的向量表达力弱**（语义依赖行列头），吃它会**挤占向量 top-k 席位**；② **RRF 按 `chunk_id` 去重 —— 同一 chunk 走两路命中只算一次，不占两个席位**。
6. **表格转自然语言用「规则展开」，不用 LLM**：表头 × 行机械拼接（`render_nl`），**零 LLM 调用**。
   原因：① 零成本；② 机械展开**天生不丢**，且**可机械验证**；③ ⚠️ 机械展开**不会"串行"** —— 而 LLM 转叙述**可能把 A 行的值写到 B 行的属性上**，**这类失真最难查**。
7. **复杂度判定只判"结构性"**（多级合并表头 / 首行空单元格）：**是"查"、不是"猜"**，**不设阈值**。
   「语义性复杂」（需跨表理解）**不判** —— 那没有干净判据，属于门控（**判定用错，代价是静默出错**）。
8. **失败模式不对称**：简单表误判成复杂 → **只花钱**；复杂表误判成简单 → **静默污染知识库**。
   → **不确定时宁可判"复杂"**（与"宁可拒答，不可编造"同源）。
9. **解析失败必须显式**：失败带**文件 / 路由决策 / 逐解析器原因**；批量灌库**逐篇 try**，一篇坏文件不中断整批，结束输出**失败清单**。

### 3.4 解析管道（2.0 新增）

**三层路由**：

```
第 1 层 文件级    后缀 + magic number 互证 → MIME → 纯文本兜底
第 2 层 解析器级  链式 fallback（首选 / 备选 / 降级）；全失败 → 显式抛错
第 3 层 切块级    table / code → 整块不切；段落·标题 → 按段切
```

**统一 IR**（`blocks.py`）：`Block{kind, text, page, raw_table, table_complex, meta}`，
`kind ∈ {paragraph, heading, table, code}`。下游**只认 IR，不认具体库**。

> ⚠️ **为什么标题要单独一类**：切块级路由要按它做「章节递归切」，混进 `paragraph` 就再也认不出来了。
>
> ⚠️ **`ParsedDoc.parser` 单独记「实际用上的」解析器名** —— 路由 + fallback 正是最容易漂移的地方，
> 必须能核实「路由**打算**用什么」≠「**实际**用了什么」。

**第 3 层的两条硬约束**（都是踩出来的）：

1. **不能逐块调用 `split_text`** —— 它靠**跨段维护"当前章节"**（标题被累积进当前块，并记为该块的 `title`）。
   逐块调用 → 标题与它后面的段落被割开 → **章节归属全丢**。所以按"**段**"切。
2. **页边界也断段** —— PDF 是"一页一块"，多页并成一段则 `page` 只能取首块 →
   **后面几页会被标上第一页的页码**，引用溯源于是显示一个**看起来可信、其实是编造**的页码。

## 4. 验证踩坑记录

### 4.1 1.0（6 个 bug）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | `GET /documents/{id}` 返回 500 | SQL `id::text` 列名是 `id`，模型要 `document_id` | 改成 `id::text AS document_id` |
| 2 | API 启动失败 `NotImplementedError` | langchain-mcp-adapters 0.1.0+ 的 `MultiServerMCPClient` 不能 `async with` | 去掉 `__aenter__/__aexit__`，直接 `get_tools()` |
| 3 | key 解析成 `# TODO: 用户自填`，LLM 报 `UnicodeEncodeError` | `.env` 里 `DEEPSEEK_API_KEY=  # TODO` 的行内注释被 python-dotenv 当成值 | 注释独立成行，key 置空 |
| 4 | 空 key 下 API 启动失败 `Missing credentials` | langchain-openai 1.6 在**构造** ChatOpenAI 时就校验 key | key 为空时跳过 agent 构建（懒初始化），/chat 返回 503 |
| 5 | 问答检索返回空 | 上传接口没接受 department/secret_level，chunk 元数据为 NULL，权限过滤把它排除了 | 上传接口加 `department`/`secret_level` Form 字段，传到 chunk |
| 6 | 新文档入库后老问题仍返回旧空结果 | 上传后没作废 Redis 缓存，旧结果被命中 | document_task 处理完成后调 `invalidate_cache()` |

**通用教训**：新版本库（langgraph/langchain-openai/langchain-mcp-adapters）API 变化大，写代码前先 introspect 实际签名，别照搬旧文档。

### 4.2 2.0（5 个·**都是"静默出错"类**）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | `.doc` / `.ppt` 在支持白名单里，**实际读不了** | **"声称支持"和"真支持"是两份清单**，各自演化 | 支持格式**以路由表为唯一事实源**（`routing.supported_extensions()`），其余**明确拒收并给原因** |
| 2 | **Word 文档里的表格全部丢失** | `loader` **只读 `doc.paragraphs`** —— 表格不在 `paragraphs` 里 | 改走统一 IR，表格成 `kind="table"` 块 |
| 3 | ⭐ **Word 的合并单元格被漏判为「简单表」** | `python-docx` 把合并文本**重复**到每个格：`['差旅标准','差旅标准','备注']` → **行长集合是齐的**，原判据（行长不齐 / 首行有空单元格）**看不出来** | **证据一直在底层 XML 里**（单元格 `tcPr/gridSpan`、`vMerge`）→ 补 `_docx_table_has_merges()` 读 XML。**两个判据互补，缺一不可** |
| 4 | ⭐ **一个语法错误在公开仓库活了 2 天** | 脚本改完**跑通了** → **又改了一处判读文案** → 引入语法错误 → **没重新验证**就推送 | 修 + 加**全仓语法普查闸**（`tests/test_syntax_sweep.py`，逐个 `ast.parse`）。**教训：要问"验的是哪个版本"，不是"验过没有"** |
| 5 | 「原表进词法 = 多一条精确召回路径」这个理由**实测为空** | 另一条验收规定「自然语言版保真」→ 自然语言版**已含原表全部 token** → `tokenize(content + raw_table)` 与 `tokenize(content)` **token 集合完全相同** | **设计保留**（无害、便宜），但把**三处注释改成实测口径**；并把「本字段独有 token 应为空」写成**可失败的测试**（**注释解释了不存在的事要修；变成断言，就同时防了下一轮**） |

**通用教训（2.0）**：**"语法通过 + 单测通过 + 我改之前验过"三件都不够** ——
本项目三次同类事故（改完没验最终产物 / 对象作用域没对准 / 描述了不存在的事），
共同点是**失败时不报错**。防线要能**主动变红**，否则等于没有。

## 5. 编码问题结论

**数据从头到尾就是 UTF-8**，没有乱码问题：
- PG `server_encoding/client_encoding = UTF8`（已确认）
- 代码源文件 UTF-8、`open(..., encoding='utf-8')` 显式声明、Redis `decode_responses=True`、FastAPI JSON 默认 UTF-8

**"乱码"纯粹是终端显示问题**：Windows 控制台默认代码页是 GBK(cp936)，和 UTF-8 对不上。数据本身正确（实测 `'员工' in chunk.content` 为 True）。

**解决**：运行会打印中文/日志的脚本时加 `PYTHONIOENCODING=utf-8`（bash 前缀 / PowerShell `$env:PYTHONIOENCODING="utf-8"`）。

**企业标准分层做法**：数据层 UTF8 + client_encoding、代码层显式 UTF-8、传输层显式 `charset=utf-8`、文档解析约定源文件 UTF-8（纯 txt 是主要坑）、显示层控制台代码页 65001。

## 7. 知识库治理方向（路线图，暂不实现）

知识库"内容治理"是独立于检索/生成的一大块工作，方向已明确但当前 demo 不实现，记录如下：

- **局部更新**：仅"原地替换无偏移"时才有意义，有增删即退回全量重建；收益只省当前文档算力，不能替代跨文档核查。
- **跨文档过期核查**：改文档 → 用变更知识点检索全库 → 输出"其他文档疑似过期 chunk"清单，人工核查。
- **治理工作流**：待改文档优先级排序（时效性/业务权重/匹配置信度/使用热度）、文档内定位辅助 + 编辑草稿、分批 + SLA + 分责任人、用户反馈通道、离线一致性巡检。
- **中心化公共知识库 + 模板化文档**：治本，但依赖文档写作规范（组织问题，非技术）。

**关键原则**：❌ 不自动改写原始文档；❌ 不靠重 embedding 修事实错误。局部更新收益有限，真正的成本在"跨文档事实冲突 + 人工核查"。

| 维度 | 评分 | 说明 |

4. **工程可复现**——锁版本 + Alembic + 单元测试，换机器能重建。

### 8.3 ⚠️ 本文档体系的一个教训
