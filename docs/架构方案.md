## 1. 项目定位

面向 B 端企业内部的知识库问答系统。用户上传文档（**PDF / Word / Excel / PPT / Markdown / txt / 代码**），
用自然语言提问，系统检索知识库、按需调用业务系统工具、生成**带引用溯源**的答案；
当检索到的候选互相矛盾时，**主动追问而不是擅自选一个**。

**2.0 的三条主张**：**可溯源 · 会拒答 · 能发现文档冲突**。
> 用户给的优先级：**禁止答错** —— 「**宁可说没有找到相关材料，也不可以乱说**」；
> 约束排序：**成本 ≥ 延迟 > 准确度 > 并发**。

**设计目标**：本地免费部署可跑 + 企业级扩展口子预留 + 后期平滑迁移（Milvus / 云 Embedding / 云 LLM）。

## 2. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| Web | FastAPI + Uvicorn | 异步、轻量、类型友好 |
| 向量存储 | PostgreSQL 17 + pgvector | 单库事务、免运维第二套 DB、与业务数据同库 |
| 词法检索 | PG 全文检索（`tsvector` + GIN）+ `jieba` | 兜底"精确词"查询；PG 自带分词器不切中文，故在 Python 侧预切 |
| 缓存 / 队列 | Redis + Arq | 缓存问答结果 + 异步文档处理，轻量 |
| Embedding | 本地 Ollama `bge-m3`（1024 维） | 免费、中文好、本地不出网、可 GPU 加速 |
| 精排 | 本地 Cross-Encoder `BAAI/bge-reranker-base`（默认） | 确定性、快；云端 LLM 精排作为**备用兜底** |
| LLM | **任意 OpenAI 兼容服务**（经 `litellm_config.yaml` 收口，实际走 ChatOpenAI） | **已解除厂商绑定**（D8）；换服务只改配置。本项目自测用 DeepSeek |
| Agent 编排 | LangGraph | 标准 ReAct 图，可插工具 |
| MCP 工具 | FastMCP（stdio） | 走真协议，上线替换真实服务只改连接 |
| 文档解析 | **三层路由**：pdfplumber / python-docx / openpyxl / python-pptx / 纯文本兜底 | 见 §5① 的解析管道；**每层都有 fallback** |

## 3. 架构分层

```
API 层        api/          upload_api, chat_api, demo_api
鉴权层        auth/         token → 用户身份（部门 + 密级）
编排层        agent/        graph_builder(LangGraph), mcp_mock_server(FastMCP), mcp_client_wrapper
检索层        rag/          retriever(混合检索 + RRF + 精排) / reranker / ambiguity / query_rewriter
抽象层        embedding/    BaseEmbedding → OllamaEmbedding / CloudEmbedding(占位)
              vector_store/ BaseVectorStore → PgVectorStore / MilvusStore(桩) + AccessFilter
数据层        db/           asyncpg 连接池 + transaction()；Alembic 迁移
缓存/任务     cache/ tasks/ Redis 缓存；Arq worker + document_task
解析层        document_parser/  routing(三层路由) + parsers(多格式) + tables(表格)
                               + blocks(统一 IR) + chunking(块级切块) + semantic_splitter + tokenizer(jieba)
横切          config/ schemas/ observability/
```

**核心设计原则**：各层通过抽象接口通信，配置驱动实现切换，业务代码不感知底层引擎。
抽象层均带**默认降级实现**——例如 `BaseVectorStore.search_lexical` 默认返回空，
不支持的实现会自动退化为纯向量检索（Milvus 无需改动）。

## 4. 数据模型

**documents（主表）**

| 字段 | 说明 |
|---|---|
| id | UUID 主键 |
| filename | 落盘文件名 |
| original_name | **用户上传时的原始文件名**（0004 迁移） |
| status | `pending` → `processing` → `completed` / `failed`（含 `deleted`） |
| version | 版本号，更新时 +1 |
| chunk_count / error | 切块数 / 失败原因 |
| created_at / updated_at | 时间戳 |
| is_deleted | 软删标记 |

**chunks（向量表）**

| 字段 | 说明 |
|---|---|
| id / document_id | 主键 / 外键（ON DELETE CASCADE） |
| chunk_index / document_version | 块序号 / 所属文档版本 |
| content / embedding | 文本 / `vector(1024)`（维度由 `EMBEDDING_DIM` 联动迁移脚本） |
| content_tsv | `tsvector`（Python 侧 jieba 切词后写入）+ GIN 索引。⚠️ **= `tokenize(content + raw_table)`** |
| department / secret_level | **权限元数据** |
| source_file | 来源文件名 |
| start_offset / end_offset / title | **溯源定位**（字符偏移 + 章节标题） |
| **page** | **1-based 页码**（0005）。⚠️ **PDF 才有**；Word/Excel 为 `NULL` —— **不编造页码** |
| **raw_table** | **原表 Markdown**（0005）。⚠️ **只进词法、不进向量** |
| **table_complex** | **结构性复杂表标记**（0005）→ 这类表的原表**也进向量** |
| is_deprecated | **废弃标记**（疑似过期，检索过滤） |
| create_time / updated_at | 时间戳 |

> ⚠️ **`page` 用 `NULL` 而不是 `0`** —— 引用溯源宁可显示"无页码"，
> 也不能显示一个**看起来可信、其实是编造**的页码。

**索引**：HNSW 向量索引、`content_tsv` GIN、`document_id`、`(department, secret_level)`、
`is_deprecated`、`is_deleted`、`updated_at`。

**一致性规则**：增删改同事务；更新 = 同事务删旧 chunk + 插新 + version+1；删除 = 软删；
检索恒带 `is_deleted=false AND is_deprecated=false`（**始终硬过滤**）。

### 4.1 内容与元数据解耦（设计原则）

> **要解决的问题**：业务字段会变、清洗规则会变、解析器会换、将来还要加图片 ——
> **难道每次都要把整个知识库重嵌一遍？**

| 变的是什么 | 要不要重嵌 |
|---|---|
| **内容**（解析 / 清洗 / 切块 / 换嵌入模型） | ✅ 要 |
| **只是业务元数据**（权限 / 部门 / 分类 / **图片路径**） | ❌ **不要** —— 只更新元数据行 |

**⭐ 本项目的有利条件**：向量库就是 **pgvector，元数据本来就在 `chunks` 表里** ——
所以"元数据与向量解耦"**现在几乎免费成立**：

```sql
UPDATE chunks SET department = '财务部' WHERE document_id = $1;   -- 不碰 embedding
```

> 这也是为将来换 **Qdrant / Milvus** 铺的路：那时改用它们的 **payload 更新 API**，
> 同样**不重算向量**。抽象层已把这条口子留好（§7）。
>
> ⚠️ 所以 **`image_path` / `table_id` 这类"将来才会填"的字段，现在就该把位置留出来** ——
> 留位置的成本是一次迁移；**不留的代价是将来为了加一列而重嵌全库**。

#### ⭐ 一个决定性的设计选择：**新增内容要成"新的块"，不要并进已有的块**

"将来引入图像识别，会不会导致全库重嵌"—— **答案取决于这一条**：

| 做法 | 后果 |
|---|---|
| 把图片描述**追加进**已有 chunk 的 `content` | ⚠️ **那个 chunk 的内容变了 → 必须重嵌**。若很多块都含图 → **大面积重嵌** |
| 图片描述**独立成一个新 chunk**（`kind="image"`） | ✅ **已有 chunk 的内容一个字都没变 → 不需要重嵌**。纯增量 |

**→ 采用后者。** 再叠上 **`content_hash` 复用**（见 §4.2）：

```
重跑时先算 content_hash：
  哈希没变 → 直接复用旧向量，不重算
  哈希变了 → 只重算这一块
```

**两条合起来**：引入图像识别 = **只为"图片块"付嵌入成本，文本块零成本**。
这正是"内容与元数据解耦"要防的那笔钱。

**现状对照**：

| 能力 | 现状 |
|---|---|
| 元数据独立更新（不重嵌） | ✅ **已有** —— `department` / `secret_level` / `page` / `raw_table` 都是普通列 |
| 文档版本号 | ✅ `documents.version` / `chunks.document_version` |
| 旧版本标记 | 🟡 `is_deprecated`（**布尔两态**） |
| **阶段版本号**（解析 / 清洗 / 切块 / 嵌入） | ❌ **没有** |
| **内容哈希**（判断"内容真的变了没"） | ❌ 没有 |
| **命中规则清单**（清洗 shadow 跑要它） | ❌ 没有 |
| **缓存键含版本** | ❌ 没有（当前 = `question + department + secret_level + top_k`） |

### 4.2 分阶段流水线（规划）

```
源文档 → 解析 → 清洗 → 切块 → 嵌入
  │       │       │       │       │
  │       │       │       │       └─ embedding_model / embedding_version
  │       │       │       └─ chunker_version / chunk_strategy
  │       │       └─ clean_rules_version / applied_rules
  │       └─ parser_version
  └─ source_hash
```

> ⚠️ **这是「版本化视角」的线性模型，不是物理位置。**
> 物理上**清洗横跨解析前后**（35 条规则分 5 组，见 §5①）——
> 但**版本号要分开记**：`parser_version` 变了要重跑全链，`clean_rules_version` 变了只重跑清洗之后。
> **把清洗并进解析层就没法分开版本化。**

**规划要加的 `chunks` 字段**：

| 字段 | 作用 | 为什么值得加 |
|---|---|---|
| `source_hash` | 源文件哈希 | **判断"内容真的变了没"** → 避免无意义重跑 |
| `content_hash` | 切块后文本哈希 | 同上；也让"重跑前后是否等价"**可验证** |
| `parser_version` | 解析器版本 | 换解析器时**精确定位**受影响范围 |
| `clean_rules_version` | 清洗规则版本 | 新增规则时只重跑"规则版本落后"的那些 |
| `applied_rules` | **本块命中了哪些清洗规则** | ⭐ 与清洗的 **shadow 跑天然是同一个东西** —— shadow 要记的就是它 |
| `chunker_version` / `chunk_strategy` | 切块版本与策略名 | 只改了表格策略 → **只重跑 `chunk_strategy='table'`** |
| `embedding_model` / `embedding_version` | 嵌入模型版本 | 换模型时**只重跑嵌入**（不重解析、不重切块） |
| `table_id` / `image_path` | 溯源 | 引用能点到**原文件的哪张表 / 哪张图** |
| `status` | `active` / `stale` / `deprecated` | `is_deprecated` 是**布尔两态**；三态才能表达"**待重跑**" |

> **成本**：一次迁移 + 灌库时多写几个值。
> **它防的是**：为加一个 `image_path` 而**把整个知识库重嵌一遍** ——
> 那笔钱完全没必要，且**重嵌期间新旧向量会混**。

### 4.3 增量重跑：**按影响范围**，不全量

| 变更 | 重解析 | 重清洗 | 重切块 | 重嵌入 |
|---|---|---|---|---|
| 只改业务元数据（权限 / 部门 / 分类） | ❌ | ❌ | ❌ | ❌ |
| 只改清洗规则 | ❌ | ✅ | 视块边界而定 | ✅ |
| 改切块策略 | ❌ | ✅ | ✅ | ✅ |
| 换解析器 | ✅ | ✅ | ✅ | ✅ |
| 换嵌入模型 | ❌ | ❌ | ❌ | ✅ |

**流程**：变更登记（记新旧版本号）→ 按元数据筛出受影响 chunk → 标记 `stale` →
按文档分批入 Arq → 重跑 → 新块 `active`、旧块 `deprecated` →
**跑评估集对比** → **通过才切缓存** → 旧版本保留一个周期后删。

> ⚠️ **"评估通过才切"不能省** —— 否则重跑 = **一次没有回滚点的全量替换**。
> 现有 `is_deprecated`（检索恒过滤）已能让"新旧并存 + 用标记切换"，**这个机制直接复用**。

### 4.4 缓存键必须含版本

**当前**：`question + department + secret_level + top_k`。
**规划加**：`clean_rules_version` / `chunker_version` / `embedding_model`。

> ⚠️ **不加会怎样**：重跑后用**同样的键**命中**旧答案** ——
> 表现为"**重跑没生效**"，而且**没有任何报错**。
> 本项目已踩过同类（上传新文档后老问题仍返回旧结果，见 `开发记录.md` §4.1 第 6 条）。

## 5. 核心链路

### ① 文档上传（异步，不阻塞）

```
POST /documents/upload (file + secret_level + 可选 document_id)
  → 鉴权：token → 部门/密级（不信任客户端传参）；校验密级不超过上传者
  → 流式写盘（50MB 上限）
  → INSERT/UPDATE documents(status=pending, version+1)
  → Arq 入队 → 返回 document_id

Worker: 三层路由 → 解析出 Block IR → 块级切块 → jieba 分词
        → bge-m3 批量嵌入 → 同事务替换 chunk → status=completed → 作废缓存
```

#### 解析管道：三层路由（**2.0 核心改动**）

```
第 1 层 文件级    后缀 + magic number 互证 → MIME → 纯文本兜底
第 2 层 解析器级  链式 fallback（首选 / 备选 / 降级）；全失败 → 显式抛错
第 3 层 切块级    table / code → 整块不切；段落·标题 → 按段切（复用 split_text）
```

> ⚠️ **第 3 层的两条硬约束**（都不是洁癖，是踩过的坑）：
> 1. **不能逐块调用 `split_text`** —— 它靠跨段维护"当前章节"，逐块调用会把标题与它后面的段落割开，
>    **章节归属全丢**。所以按"**段**"切：连续文本块合为一段。
> 2. **页边界也断段** —— 多页并成一段时 `page` 只能取首块，**后面几页会被标上第一页的页码**。

**解析产物是统一 IR**（`blocks.py`）：

```python
Block{kind, text, page, raw_table, table_complex, meta}
# kind ∈ {paragraph, heading, table, code}
```

下游（切块 / 入库 / 检索）**只认 IR，不认具体是哪个库解析出来的**。
`ParsedDoc.parser` 另外记下**实际用上的**解析器名 —— 便于核实「路由**打算**用什么」≠「**实际**用了什么」。

> ⚠️ **图片不在 IR 里** —— 当前解析器**不提取图片**，图片是**静默丢失**的
> （全管道与图片相关的只有一行 warning「第 N 页无文本层，可能是扫描件，需 OCR」）。
> 这是 2.0 的**已知缺口**，见 `改进计划.md` **2.0-21**。

**表格处理**（`tables.py`）：

| 产物 | 内容 | 向量 | 词法 |
|---|---|---|---|
| `content` | **自然语言版**（`render_nl`：表头 × 行**规则展开**成自包含句子，**零 LLM 调用**） | ✅ | ✅ |
| `raw_table` | **原表 Markdown** | ❌ | ✅ |
| `table_complex` | **结构性复杂**判定：合并单元格（`gridSpan` / `vMerge`）、首行全空 | 这类**额外**进 | ✅ |

> **为什么"规则展开"而不是 LLM 转写**：① 零成本；② **机械展开天生不丢**，且**可机械验证**；
> ③ ⚠️ **机械展开不会"串行"** —— 而 LLM 转叙述**可能把 A 行的值写到 B 行的属性上**，
> **这类失真最难查**。
>
> **复杂度判定只判"结构性"**（是**查**、不是**猜**）：多级合并表头 / 首行空单元格都是**确定性事实**。
> **"语义性复杂"（需跨表理解）不判** —— 那没有干净判据，属于门控。**不设阈值**。

#### 清洗：**横跨管道的规则集**（规划，**未实现**）

⚠️ **常见误解**：以为清洗是"解析之后的一个步骤"。
实际它按**作用范围**分布在管道各处 —— 共 **35 条规则**（`CLN-001`~`CLN-035`），按时机分 5 组：

| 组 | 规则 | 做什么 | 为什么在这个位置 |
|---|---|---|---|
| **解析前** | `CLN-013`~`017` | 编码 / 换行统一（BOM、控制字符、`\r\n`） | **必须在解析器之前** —— 否则解析器读进来就是乱的 |
| **解析中** | `CLN-001`~`009` | 去 HTML/XML 标签、导航、广告、页眉页脚 | 依赖解析器给出的**块结构** |
| **解析后** | `CLN-010`~`012` | 去重（精确 / 近似 / 段落） | 需要**全文**视角 |
| **规范化** | `CLN-018`~`022` | 空行 / 空格 / 全角半角 / 繁简 / 乱码 | 纯字符层 |
| **富化** | `CLN-023`~`035` | 语言 / 时间 / 来源 / **权限** / 章节 / **表格** / 代码块 | **大部分已在解析层实现** |

> ⭐ **所以"清洗属于解析层吗"的答案是「横跨」**：
> `CLN-026` 权限标签 / `CLN-029` 章节识别 / `CLN-030` 表格提取 / `CLN-032` 代码块保留
> —— 这些 `keep` 类**已经在解析层做了**（见上文的三层路由与表格处理）；
> 待做的是 `remove` / `normalize` 那几组。
>
> ⚠️ **这直接影响版本化**：`parser_version` 与 `clean_rules_version` **必须分开记**，
> 因为它们对应**不同的重跑范围**（换解析器要重跑全链；改清洗规则只重跑清洗之后）。
> 若把清洗并进解析层，**就没法分开版本化** —— 这也是 §4.2 把两者分成两个字段的原因。

**准确性怎么保证 —— 靠三个机制，不是靠"规则写得好"**：

| 机制 | 说明 |
|---|---|
| **1. `flag` 动作** | 拿不准的**只标记、不删**。`CLN-022`（乱码）与 `CLN-024`（低质过滤）误伤风险标"高/中" → 只 `flag` |
| **2. shadow 先跑** | 只记录**命中量**（写进 chunk 的 `applied_rules`）、**不改变输出** → 量出**误伤率**后再逐条放行 |
| **3. 版本 + 评估闸** | `clean_rules_version` 决定重跑范围（§4.3）；**评估通过才切**（§4.3 末），可回滚 |

> ⚠️ **"保证准确性"这个说法本身要改写。** 清洗**无法被"保证"准确** —— 它能做到的是
> **可见**（命中了哪些规则，`applied_rules`）、**可量**（误伤率，shadow 跑）、**可回滚**（版本 + 评估闸）。
> **没有这三条，"准确性"就是自说自话。**
>
> **取向**：**漏洗**（该洗的没洗）→ 噪声进库，**可被发现**（检索质量下降）；
> **误洗**（不该洗的洗掉了）→ **静默丢信息**，**不可发现**。
> → **宁可少洗，不可错洗。** 这与"宁可拒答，不可编造"同源。

### ② RAG 问答（同步）

```
POST /chat (question)
  → 鉴权（部门/密级取自 token）
  → Redis 缓存检查（key 含 question + department + secret_level + top_k）
  → retrieve()：
        词法检索(ts_rank) ┐
                          ├→ RRF 融合 → 精排（本地 CE，取 top_k）
        向量检索(HNSW)   ┘
  → 歧义判定（云端 LLM）：候选之间是否矛盾？
        ├─ 歧义 → 生成澄清话术，直接返回（need_clarification=true + clarify_options）
        └─ 不歧义 → Agent 生成（LangGraph，按需调 MCP 工具）
  → 引用校验（解析答案里的 [来源N]，只返回 LLM **实际引用**的块）
  → 写缓存 → 返回 {answer, sources[]}
```

> ⚠️ **两个入口的步骤顺序不同**：`/demo/ask`（演示入口）是 `retrieve → 生成 → 歧义判定`，
> 且显式传入 `use_hybrid` / `use_rerank`，**会覆盖 `settings` 里的同名开关**。

> ⚠️ **歧义判定在检索之后**（它需要判断"候选之间是否矛盾"，存在真实数据依赖，
> 无法与检索并行）。

### ③ 鉴权

`Authorization: Bearer <token>` → `DEMO_USERS` 映射到（姓名 / 部门 / 密级）。
演示用静态 token，真实环境替换为 JWT / SSO。

## 6. 关键设计决策

> 完整理由见 `开发记录.md`。以下为结论。

1. **RAG 管道手写，只有 Agent 编排用框架**（LangGraph）。为"模块解耦 + 预留扩展口子 + 可替换"服务——
   框架会把抽象藏起来，不利于后期切 Milvus / 云 embedding。
2. **LLM 走 `langchain_openai.ChatOpenAI` 指向任意 OpenAI 兼容服务**（`litellm_config.yaml` 收口）。
   LangGraph 工具调用需要 LangChain 聊天模型。**已解除厂商绑定**（D8）—— 换服务只改配置。
   ⚠️ 用推理模型时**必须关思考链**：`reasoning_content`（思考）与 `content`（结论）**共用同一份 `max_tokens`**，
   思考吃满则 `content` 为空 → 精排**静默回退成粗排顺序**且不报错。
3. **抽象层为平滑迁移铺路**：`BaseEmbedding`（切云 embedding）、`BaseVectorStore`（切 Milvus）、
   `AccessFilter`（两引擎过滤语义统一）、`VECTOR_STORE` 配置开关。
4. **Milvus 迁移用蓝绿策略，不搞永久双写**：平时单写 PG（事实源），迁移时倒灌 + 短暂双写 + 切配置 + 回滚；
   PG 索引永不删，作回滚快照。`updated_at` / `is_deleted` 就是为增量同步预留的。
5. **权限过滤在服务端**：`department` / `secret_level` 取自 token，不接受客户端参数。
6. **精排默认本地 Cross-Encoder**：确定性、无云端延迟与成本；云端 LLM 精排仅作兜底。
   ⚠️ 工厂当前的判断是"值恰为 `local` 才用本地"，未知值会落到 LLM——
   部署时需确认实际生效的后端（见 `改进计划.md`）。
7. **表格 = 一份检索面 + 一份随行**（2.0-1）：`content` 是自然语言版（进向量 + 词法），
   `raw_table` 是原表 Markdown（**只进词法**）。
   **理由**：① 裸表的向量表达力弱（语义依赖行列头），吃它会**挤占向量 top-k 席位**；
   ② **RRF 按 `chunk_id` 去重 —— 同一 chunk 走两路命中只算一次，不占两个席位**。
8. **失败模式不对称**：简单表误判成复杂 → **只花钱**；复杂表误判成简单 → **静默污染知识库**。
   → **不确定时宁可判"复杂"**（与"宁可拒答，不可编造"同源）。
   理由**不是"成本无所谓"**，而是**失败模式不对称**。
9. **解析失败必须显式**（2.0-3）：失败带**文件 / 路由决策 / 逐解析器原因**；
   批量灌库**逐篇 try**，一篇坏文件不中断整批，结束输出**失败清单**。
10. **内容与元数据解耦**（见 §4.1）：解析 / 清洗 / 切块 / 嵌入属于**内容**，变了要重嵌；
    权限 / 部门 / 分类 / 图片路径属于**元数据**，变了**只更新一行**。
    ⚠️ **为"将来才会填"的字段（`image_path` / `table_id`）现在就留位置** ——
    留位置的成本是一次迁移；**不留的代价是将来为加一列而重嵌全库**。
11. **重跑按影响范围，且"评估通过才切"**（见 §4.3）：
    流水线各阶段带版本号 → 变更时能**筛出受影响的那部分**，而不是全量重建；
    新旧并用 `is_deprecated` 并存，**评估没通过就能退回**。

## 9. 已知边界（未实现）

| 类别 | 未实现项 |
|---|---|
| 对话 | 多轮对话（LangGraph checkpointer）、流式输出（SSE） |
| Agent | **检索不是 Agent 的工具**（当前是前置步骤，Agent 无法决定"要不要检索"） |
| 检索 | 检索盲区（部分题 3 种问法全 miss）；MMR 经诊断已跳过；相似度阈值经探查不可分 |

| 清洗 | ⚠️ **`remove` / `normalize` 那几组规则完全未实现**（管道此步为直通）—— 规划共 **35 条**（`CLN-001`~`035`），按作用范围**横跨解析前后**；其中 `keep` 类（权限 / 章节 / 表格 / 代码块）**已随解析层落地**（见 §5①） |
| 表格 | ⚠️ **表格识别方式未复核**：`pdfplumber.extract_tables()` 在真实语料的 PDF 上**返回 0 张表**（2026-09-30 实测）—— 无框线表格识别不出来 |
| 运维 | OTel 真埋点、降级兜底、水平扩展、前端界面 |
| 治理 | 知识生命周期：局部更新、过期核查、责任人工作流 |
| 版本化 | ⚠️ **没有阶段版本号**（`parser_version` / `clean_rules_version` / `chunker_version` / `embedding_model`）与**内容哈希** → 变更时**无法按影响范围筛选**，只能全量重跑；`is_deprecated` 是**布尔两态**，缺"待重跑"这一态；**缓存键不含版本**（见 §4.1/§4.4） |

## 10. 演进路线（**设计预留，未排期**）

> **两条原则**：**先低成本，后升级** ｜ **判据先行，不事后找理由**。
> 下表只说明"将来往哪走、以什么为切换依据"，**不代表已排期**。

| 顺序 | 动作 | 触发条件 / 说明 |
|---|---|---|
| 1 | **元数据版本字段**（§4.2） | **成本低，且是后面一切"增量重跑"的地基** |
| 2 | **增量重跑**（§4.3） | 依赖第 1 步 |
| 3 | **结构化中间格式**（版面感知解析：MinerU / Docling 等） | ⚠️ **先用真实语料证明必要性** —— 表格识别不到，**是否真的让用户答不出来？** 证明不了就先不上（**能验证 ≠ 能迁移**） |
| 4 | **向量库升级**（Qdrant / Milvus） | 唯一真收益是**多向量 / 命名向量**与**影子索引**；**标量过滤与元数据更新，pgvector 已经能做**（§4.1） |
| 5 | **数据血缘 / 轻量数据目录** | 需要"**改一条规则 → 自动列出受影响的文档与 chunk**"时 |
| 6 | **LLM Wiki 增量编译** | 素材不可变、编译结果可重建；适用于**知识相对稳定、需要持续维护**的场景 |
| 7 | **轻量 KG / Ontology** | ⚠️ **判据必须提前定死**（见下）。**KG 是最后一步** |

**KG 的引入判据（提前定死，避免"事后找理由"）**：

| 判据 | 阈值 | 动作 |
|---|---|---|
| 多跳类 Recall@5 | < 60% | 考虑 KG |
| 实体消歧错误率 | > 15% | 考虑 KG |
| 事实冲突率 | > 10% | 考虑 KG 校验层 |
| **单跳事实 Recall@5** | **< 85%** | **先修 RAG，别上 KG** |
| **表格数值命中率** | **< 70%** | **先修表格入库，别上 KG** |

> ⚠️ **只有「多跳 / 消歧 / 冲突」类指标差，且「单跳 + 表格」已达标，才说明 KG 有独立价值。**
> 否则上 KG 只是**用一个更贵的方案，掩盖解析与切块本身的问题**。
